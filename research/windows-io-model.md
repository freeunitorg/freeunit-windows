# Windows I/O event model for FreeUnit: design study

Date: 2026-10-07. Scope: which Windows event model fits FreeUnit's readiness-based engine, with API facts, precedents, platform targets and a staged plan.

Conventions. Code references are written `path:line@872bf041` and resolve to `https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/<path>#L<line>`. The io_uring notes cited here are public on a fork at commit 6ee2a59d: [docs/io_uring](https://github.com/andypost/unit/tree/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring). Microsoft API facts come from learn.microsoft.com. Third-party source is pinned to a tag or commit. "Inference" marks a conclusion drawn from the cited facts, not a fact found in a source.

Answer in brief. The hypothesis "use I/O completion ports" holds for the wait object and fails for the I/O model. An IOCP is the only scalable thing a Windows thread can wait on, and every scalable option below uses one. But FreeUnit's connection and port layers are readiness loops, so the engine should get readiness from the IOCP, not completed reads and writes. On Windows 11 and Windows Server 2022 or later (build 20348+), ProcessSocketNotifications provides documented level, edge, oneshot and persistent readiness on an IOCP, with a terminal REMOVE notification for safe teardown. It maps onto `nxt_event_interface_t` almost one to one. Recommended path: bring up the port on a WSAPoll engine cloned from `nxt_poll_engine.c`, then make a ProcessSocketNotifications engine the default, gated by a runtime probe. Do not start with overlapped completion I/O: the io_uring effort measured "parity-minus" for its completion stage, and a completion engine would replace the conn and port layers wholesale.

## 1. What does FreeUnit's engine contract require, and what did the io_uring effort teach?

### Takeaway
The engine is a readiness vtable: batched interest changes, a cheap user-space BLOCKED state, oneshot, a level-triggered listener shared by all router engines, a doorbell for cross-thread posts, signal routing, and a millisecond poll timeout. Sockets and fds are `int`. The io_uring effort shows that a completion-capable backend under this contract needs generation-checked teardown and an EOF shim to be correct, and that it bought parity throughput at a CPU cost, not a win.

What the io_uring effort recorded:
- Listener: "An edge-triggered or oneshot listener would silently stall whenever the accept batch is smaller than the backlog. This is the single hardest constraint for a completion/edge bridge to reproduce." - Doorbell: "arbitrary threads may call post/signal; the wake primitive ... must be async-signal-safe and thread-safe, but the actual work payload travels through the locked work queue, never through the wake primitive itself". [engine-contract.md §7](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/engine-contract.md)
- Engine creation: "there is no retry-next-engine loop"; a new engine that fails `create()` "will not transparently degrade to epoll; selection must be gated before create". [engine-contract.md §11.4](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/engine-contract.md). The branch later moved a fallback into `nxt_event_engine_create()`/`_change()` "so ring exhaustion in any process degrades to epoll instead of dying". - Buffers: engine buffers "are owned by the engine thread and reused synchronously after the I/O call returns"; a completion engine that keeps a buffer registered with the kernel across a poll boundary would violate this. [engine-contract.md §12.5](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/engine-contract.md)
- The contract lists 12 readiness assumptions outside the engine (recvbuf EAGAIN loop, port drain loops, cheap BLOCKED, level listener, buffer reuse, write-fairness zero timer, EOF shim, deferred close, change-batch pointer lifetime, error-only events, doorbell). It concludes that a full completion-mode engine "would additionally invalidate items 1-2, 4, 6 and require replacing the conn-io and port-socket layers wholesale". [engine-contract.md §16, §16.1](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/engine-contract.md)
- Close is the main hazard: closing an fd with an operation in flight risks a late completion against reused user data. The mitigation is a generation counter in every arming, explicit removal before close, and not freeing a slot until it is quiesced. [engine-contract.md §16 item 9](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/engine-contract.md); [design.md §1.6](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md)
- Multishot poll turned out edge-like: "A readiness indication consumed together with data (e.g. a response and FIN arriving in one wakeup ...) is gone forever". The engine needed the epoll-edge EOF shim; the bug showed as a proxy keepalive wedge with "~90% timeouts". [design.md §1.7a](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md)
- Listener herd: POLL_ADD "has no EXCLUSIVE analogue", so every worker ring woke for every connection. [design.md §1.8](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md). Multishot accept then "funneled 32/32 connections to one ring; 7/8 workers idle"; the fix was oneshot accept re-armed per completion. [design.md §2.1a](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md), [results-stage2.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage2.md)
- Sends stayed synchronous ("Stage 2 = async recv/accept in, synchronous send out") and port sockets stayed in poll mode because fd passing "dwarfs any syscall saving on this low-volume path". [design.md §2.3, §2.4](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md)
- Cross-thread constraint: router worker engines are created on the router main thread and polled on worker threads, which broke SINGLE_ISSUER rings. [design.md §2.5](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md)
- Measured, stage 1 (poll-mode bridge): throughput parity; router CPU per request +1.6% to +24.7% (oha) and -0.6% to +49.5% (ab), worst on connection-heavy scenarios. [results-stage1.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage1.md)

The projected wins "were always in the deferred RECV tier", which was not landed. [results-stage2.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage2.md)

### Inferences
Lessons that transfer to Windows:
1. Gate the engine before `create()`. A Windows engine that needs ProcessSocketNotifications must probe for it (GetProcAddress on ws2_32.dll, as Microsoft's WIL does, see section 2) and fall back to another engine, because FreeUnit has no retry loop.
2. Teardown is the correctness core. On Windows the equivalent hazards are a ProcessSocketNotifications packet queued before `closesocket()`, an AFD poll IOCTL still pending, or an overlapped operation whose OVERLAPPED and buffer must outlive the cancel. Generation-tagged completion keys plus "do not free until the terminal event" carry over directly.
3. Prefer level or level+oneshot semantics so `nxt_unix_conn_io` works unchanged. Edge semantics need an RDHUP source for the EOF shim; AFD poll has one (AFD_POLL_DISCONNECT), ProcessSocketNotifications documents none (see section 7).
4. The listener needs level re-fire. On Windows a second constraint appears: a socket can be registered with only one IOCP, which collides with every router engine sharing one listener (section 2 and section 4).
5. Keep sends synchronous and the port layer readiness-based at first, as the io_uring work did.
6. Expect parity at best from a readiness bridge. A CPU win, if any, lives in completion receive, and that needs conn_io and buffer-ownership work.
7. Issue I/O from the engine's own thread. FreeUnit already creates router engines on one thread and runs them on another; on Windows, I/O issued by a thread can be cancelled when that thread exits (section 2).
8. The `int` typing is a porting item of its own: SOCKET is unsigned pointer-sized, and the select engine's fd-indexed array and bit scan cannot work with Windows handles.

### Gaps
- `nxt_conn_close.c` was not re-read at 872bf041 in this pass; the claim that the close path already defers `close(2)` while `close()` returns true rests on the io_uring contract §5 and §16 item 9 and on `src/nxt_epoll_engine.c:410-416@872bf041`.
- The local internals note on the event engine was read for orientation but is not published, so nothing here depends on it.

## 2. Which Windows APIs exist, from which version, and with what semantics?

### Takeaway
ProcessSocketNotifications is the only documented readiness API that scales; it requires build 20348 (Windows Server 2022) on both client and server, which in practice means Windows 11 or Server 2022 and later. WSAPoll and select are documented but O(n) and sockets-only. AFD poll is undocumented. Classic IOCP, RIO and TransmitFile are long-standing completion APIs. AF_UNIX exists but only as SOCK_STREAM without descriptor passing, and anonymous pipes cannot do overlapped I/O.

### Inferences
- In practice ProcessSocketNotifications requires Windows 11 (build 22000 and later) or Windows Server 2022/2025. The "Windows 10" in Microsoft's requirement line is the kernel family name: no Windows 10 client release ever had build 20348, and the export dumps confirm its absence on 19045.
- Edge mode in ProcessSocketNotifications has the same "drain to WSAEWOULDBLOCK" contract as EPOLLET, and the documentation gives no RDHUP-style event. So the io_uring EOF wedge can recur with edge registrations unless HANGUP fires on a graceful FIN. Level plus oneshot avoids the question.
- The one-IOCP-per-socket rule applies to ProcessSocketNotifications registrations ("A socket may be associated with only a single I/O completion port", concept page) and to overlapped I/O ("A handle can be associated with only one I/O completion port", [CreateIoCompletionPort](https://learn.microsoft.com/en-us/windows/win32/fileio/createiocompletionport)). AcceptEx is issued on the listening socket, so its completions can reach only that socket's port; the AcceptEx page does not say this directly, so this part is an inference. FreeUnit's router, where every worker engine registers the shared listener, cannot keep that shape with per-engine IOCPs. AFD poll does not have this restriction, because the IOCTL goes through a separate AFD helper handle (wepoll: "Sockets can be added to multiple epoll sets", section 3).
- The select rule "a single service provider" per call probably means an AF_UNIX socket and a TCP socket cannot be waited on together. The WSAPoll page states no such rule. Both need a test (section 7).
- The 2000-era locked-page and non-paged-pool numbers are historical; the principle that every pending overlapped operation pins resources still motivates zero-byte reads and readiness APIs.

### Gaps
- No Microsoft document gives a ProcessSocketNotifications behaviour for a graceful half-close, for OP_DISABLE followed by OP_ENABLE, or for AF_UNIX sockets.
- I found no official statement on the support status of IOCTL_AFD_POLL.
- NtAssociateWaitCompletionPacket's page lists no minimum Windows version.
- The original Microsoft text that introduced the zero-byte receive technique was not found; the October 2000 article explains the locked-page motivation but does not describe zero-byte receives.
- The ProcessSocketNotifications page says re-registration overwrites the existing registration; the concept page says a socket may be registered with a port only once and that a new completion key needs OP_REMOVE, a wait for REMOVE, and a new registration. Neither says which rule applies to a changed event filter with the same key.
- Named pipe message mode (PIPE_TYPE_MESSAGE, ERROR_MORE_DATA), PIPE_REJECT_REMOTE_CLIENTS, the access rights DuplicateHandle needs, and WSADuplicateSocket caveats were not verified in this pass.

## 3. What did other servers and runtimes choose on Windows, and how did it turn out?

### Takeaway
Two families exist. Portable readiness runtimes moved to AFD poll on an IOCP: the JDK's default Windows selector since JDK 17, Rust mio and tokio, libuv's uv_poll, libevent's wepoll backend (used by Envoy), libzmq's default Windows poller, and c-ares. The only project found that moved a whole socket backend to ProcessSocketNotifications is Pony (0.66.0, 2026-06-29), which dropped Windows 10 to do it. Completion-native systems (libuv TCP, Go, .NET, Erlang's socket NIF, Python asyncio, Apache) were designed around IOCP and own their buffers. Readiness-loop servers ported to Windows stayed on select or poll (nginx, libev) or emulated readiness on completions and were later abandoned (Redis by MS Open Tech); nginx's IOCP module was never finished.

### Inferences
- AFD poll is undocumented but de facto stable: the JDK has shipped it as the default Windows selector since JDK 17 (2021), and libuv, mio/tokio, libzmq, Envoy and c-ares depend on it. A Windows change that broke it would break all of them.
- The JDK numbers show the property that matters for FreeUnit: cost per wait is flat in the number of idle connections with AFD poll, and linear with select. WSAPoll is expected to scale like select because it scans every element (no WSAPoll measurement found).
- Pony is the closest analogue to FreeUnit: a runtime with epoll and kqueue backends that wanted the same readiness model on Windows, chose ProcessSocketNotifications, and accepted the Windows 10 cut.
- Readiness emulated on completions (Redis on Windows) needed a virtual fd layer and fake write readiness, the same two problems FreeUnit would face with O3.
- Apache's accept-thread plus IOCP work queue is a working precedent for handing accepted connections to other threads, which the one-IOCP-per-socket rule may force on FreeUnit's router.
- Envoy shows that Windows support costs maintenance far beyond the event engine (CI, release and security processes), and that tails were worse than on Linux even with a scalable poller.

### Gaps
- No public benchmark of ProcessSocketNotifications or of zero-byte-read readiness.
- No public description of Memurai's I/O design was found; MS Open Tech gave no reason for stopping beyond the README notice.
- Not verified in this pass: which Go release first used NtAssociateWaitCompletionPacket; .NET's IOCP thread model and the UseWindowsThreadPool option; Boost.Asio's source for async_wait; the first OTP release with the IOCP socket backend; Envoy's first release with Windows support.

## 4. How would each option implement `nxt_event_interface_t`?

### Takeaway
O1 (ProcessSocketNotifications) is the closest fit: native level and oneshot, batched re-arm inside the wait call, a terminal REMOVE for safe close, and PostQueuedCompletionStatus as the doorbell. Its costs are the build 20348 floor and the one-IOCP-per-socket rule, which breaks the shared router listener. O2 (AFD poll) keeps the shared listener and runs on any supported Windows, at the price of an undocumented interface and one IOCTL per re-arm. O5 (WSAPoll) is the cheapest bring-up. O3 and O4 conflict with FreeUnit's readiness design, and O6 does not scale and cannot mix providers.

- O4 (true completion mode): the vtable shrinks to registration of handles with the IOCP, and the work moves into a new conn_io: overlapped WSARecv into buffers the kernel owns until completion, overlapped WSASend with pinned buffers, AcceptEx, ConnectEx and TransmitFile. The port layer would need overlapped pipe or socket I/O. This is the io_uring "stage 2" shape that the contract says replaces the conn-io and port-socket layers wholesale, and whose accept tier measured parity-minus.
- O6 (select): the same mapping as O5, but `src/nxt_select_engine.c@872bf041` must stop indexing by fd (`:77`, `:150`) and stop scanning bit positions (`:344-383`), FD_SETSIZE must be raised at compile time, and one call cannot mix providers.
- Shared-listener consequence: with O1, O3 and O4, each listening socket belongs to one engine's IOCP. FreeUnit then needs either one accepting engine that posts accepted sockets to the others (Apache's model) or a single shared IOCP across router threads, which conflicts with engine-owned connections and work queues. With O2 every engine can keep polling the shared listener, as today, but every engine wakes for every connection. In io_uring stage 1 that herd was named the dominant cause of the +24.7% (oha) to +49.5% (ab) router CPU per request on the Connection: close scenario.
- Ports: the IOCP-based options (O1 to O4) can also carry named-pipe completions on the same port ("arbitrary completions can be dequeued", PSN concept page), so a port transport on named pipes would still be served by one wait. O5 and O6 can wait only on sockets, which pushes the port transport to AF_UNIX stream sockets.

### Gaps
- All sizes are estimates. No Windows engine for FreeUnit exists to measure.
- Whether OP_ENABLE with a reduced filter, or with SOCK_NOTIFY_REGISTER_EVENT_NONE, behaves as assumed in the O1 column is untested (section 7, questions 1 and 2).

## 6. Recommended staged path, and what the io_uring results say about expectations

### Takeaway
Port the platform layer first, bring it up on a WSAPoll engine, then make a ProcessSocketNotifications engine in level plus oneshot mode the default behind a runtime probe. Add completion features only where a measurement shows a gain. Expect correctness and O(ready) scaling, not an engine that beats Linux epoll: the io_uring effort under the same contract reached parity throughput with more CPU.

### Cited Findings
- io_uring stage 1 (poll-mode bridge): throughput parity; router CPU per request up to +24.7% (oha) and +49.5% (ab) on the Connection: close scenario, where the listener herd was the dominant cause. Stage 2 (completion accept): "parity-minus". [results-stage1.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage1.md), [results-stage2.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage2.md)
- ProcessSocketNotifications registers and retrieves in one call, and its concept page recommends one-shot level-triggered registrations. [ProcessSocketNotifications](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-processsocketnotifications), [concept page](https://learn.microsoft.com/en-us/windows/win32/winsock/winsock-socket-state-notifications)
- Pony uses PostQueuedCompletionStatus with the signal number in the byte count, and frees state only after REMOVE. [sock_notify.c](https://github.com/ponylang/ponyc/blob/0.67.0/src/libponyrt/asio/sock_notify.c#L92-L116)
- WIL gates the API with GetProcAddress. [wil/network.h#L557-L660](https://github.com/microsoft/wil/blob/f6f3069ab39fb19c1f89fa5f2d3aa8a1118ace43/include/wil/network.h#L557-L660)
- nginx on Windows sends files with read plus WSASend, and Apache uses TransmitFile only with EnableSendfile On, in 64 KiB segments (section 3).
- TransmitFile is limited to two concurrent operations on client editions (section 2).

### Inferences
Stage 0: platform layer, independent of the engine (probably the largest work item):
- Types: make `nxt_socket_t` a pointer-sized unsigned type on Windows with an explicit invalid value, and audit `== -1` and `< 0` checks against it; decide how `nxt_fd_t` represents files (HANDLE or a CRT descriptor).
- Errors: map WSAGetLastError and GetLastError into `nxt_err_t`; WSAEWOULDBLOCK becomes NXT_EAGAIN.
- Port IPC: replace `socketpair(AF_UNIX, SOCK_DGRAM)` plus SCM_RIGHTS and SO_PASSCRED. Candidates: AF_UNIX SOCK_STREAM with length-prefixed frames, or named pipes in message mode. Pass handles with DuplicateHandle brokered by the main process and sockets with WSADuplicateSocket; keep the shared-memory queue (CreateFileMapping) and its 0-to-1 notify rule. The choice depends on questions 4, 5 and 13 in section 7. Only the final owner of a handle should associate it with an IOCP, because duplicated or inherited handles keep completing to the port of the original association (CreateIoCompletionPort, section 2).
- Processes: no fork. Child exit becomes a wait on the process handle that posts to the main engine (RegisterWaitForSingleObject callback or NtAssociateWaitCompletionPacket); job objects are a kill-all safety net only, because their exit messages are not guaranteed.
- Signals: console and service control handlers run on their own threads and call `nxt_event_engine_signal()` with a mapped signal number. Log reopening (SIGUSR1 today) can map to a user-defined service control code in the 128 to 255 range, or to a request on the control API.
- Static files: read plus send through the existing non-sendfile path, with ReadFile in place of mmap (`src/nxt_conn_write.c:295-316@872bf041` is the mmap fallback to replace). nginx/Windows does the same. For large files, the read can move to an overlapped ReadFile that completes on the engine IOCP, or to the existing blocking thread pool (inference; not measured).

Stage 1: bring-up engine, WSAPoll (O5):
- Clone `nxt_poll_engine.c` (737 lines): key the hash by SOCKET, keep level semantics and `nxt_unix_conn_io`, keep oneshot emulation by removal.
- Replace the self-pipe doorbell with a connected socket pair (AF_UNIX stream or loopback TCP), because WSAPoll waits only on sockets.
- On builds before Windows 10 version 2004, add a connect timeout plus SO_ERROR check.
- Why first: the set lives in user space, so there is no kernel-side registration to outlive a close. Platform-layer bugs will not be confused with engine teardown bugs, which the io_uring work found to be the hardest class. It also runs on every Windows version, including Windows 10 developer machines.
- Exit criterion: the existing test suite passes on Windows with this engine.

Stage 2: performance engine, ProcessSocketNotifications (O1):
- Mode: LEVEL with ONESHOT for connections and ports, re-armed after each delivery like the eventport engine; BLOCKED directions are latched and not re-armed. Level semantics keep `nxt_unix_conn_io` and avoid the EOF shim.
- Batching: queue registrations in a SOCK_NOTIFY_REGISTRATION array, as epoll queues changes, and commit them in the same ProcessSocketNotifications call that waits. A re-arm then costs no extra kernel transition.
- Close: queue OP_REMOVE and have `close()` report "changing" until the REMOVE packet arrives; tag completion keys with a slot generation so that packets queued before any direct `closesocket()` are dropped (the io_uring §1.6 invariant).
- Doorbell and signals: PostQueuedCompletionStatus with a reserved key and the signal number in the byte count.
- Listener: one engine owns each listening socket. It accepts with the existing batch loop on LEVEL and PERSISTENT readiness and hands sockets to worker engines through `nxt_event_engine_post()`, as Apache's accept thread feeds its workers. Measure this against the AFD herd alternative before committing (question 6).
- Gate: probe `GetProcAddress(ws2_32, "ProcessSocketNotifications")` and a test registration before `create()`, and fall back to the WSAPoll engine, because FreeUnit has no retry loop.
- Exit criterion: same tests as stage 1; flat cost per ready event from 100 to 10,000 idle connections in a JDK-style microbenchmark; router CPU per request reported with the io_uring harness method.

Stage 3: measured extras, each only with a measured gain:
- TransmitFile for large static files as an overlapped operation on server editions, completing on the same IOCP (needs question 3). Client editions keep read plus send because of the two-operation limit.
- AcceptEx on the owning engine if accept rate is the bottleneck, as the concept page recommends for accept scale-out.
- An AFD poll engine (O2) only if production support for Windows 10 or Server 2019 becomes a requirement; wepoll and mio are the references.
- Completion receive (O4 or RIO) last, scoped like the io_uring RECV tier and only after buffer ownership across poll is solved.

Not recommended: O3 as the main engine (no write readiness, the Redis precedent), O6 (FD_SETSIZE and single-provider limits), and a full O4 now (the contract says it replaces the conn and port layers, and the comparable io_uring stage did not win).

Expectations:
- A readiness engine adds no data-path savings: recv and send stay synchronous, as in io_uring stage 1. Gains over WSAPoll appear only as connection counts grow.
- Windows has its own tail-latency costs (Envoy reported worse tails than on Linux, especially with TLS), so a Windows FreeUnit should be judged against itself across engines, not against Linux.

### Gaps
- No Windows measurement of any option exists for FreeUnit; the plan's exit criteria are the measurement plan.
- The size of Stage 0 was not estimated; it covers process creation, IPC, signals and types, and is likely larger than any engine.

## 7. Open questions and the experiment that settles each

### Takeaway
Six unknowns decide the design: ProcessSocketNotifications behaviour on half-close and on disable and re-enable, whether it coexists with overlapped I/O and with AF_UNIX sockets, whether one wait can mix AF_UNIX and TCP sockets, and which listener ownership model costs least. Each is settled by a short C program or a prototype measurement on Windows Server 2022 or Windows 11.

### Cited Findings
- Microsoft's documentation leaves these points open: HANGUP is defined only as "disconnected or aborted"; OP_ENABLE and OP_DISABLE refer to a SOCK_NOTIFY_EVENT_DISABLE notification that the SDK header does not define; AF_UNIX support is not mentioned; the concept page warns against one IOCP per thread. [SOCK_NOTIFY_REGISTRATION](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/ns-winsock2-sock_notify_registration), [header copy](https://github.com/hughbe/windows-sdk-headers/blob/ba323740b76a78cde3a296e978f8401a5b6b3426/Include/10.0.20348.0/um/WinSock2.h#L4156-L4210), [concept page](https://learn.microsoft.com/en-us/windows/win32/winsock/winsock-socket-state-notifications)
- select requires one provider per call; WSAPoll states no such rule. [select](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select), [WSAPoll](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsapoll)
- I/O issued by a thread is cancelled when the thread exits, per the TransmitFile page. [TransmitFile](https://learn.microsoft.com/en-us/windows/win32/api/mswsock/nf-mswsock-transmitfile)
- Job object exit messages are not guaranteed. [JOBOBJECT_ASSOCIATE_COMPLETION_PORT](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_associate_completion_port)

### Inferences
| # | Question | Why it matters | Experiment that settles it |
|---|---|---|---|
| 1 | Does SOCK_NOTIFY_EVENT_HANGUP fire on a graceful FIN (peer `shutdown(SD_SEND)`), or only on full close and abort? Does an EDGE registration lose EOF when data and FIN arrive together? | Decides whether edge mode is usable without an RDHUP source; level plus oneshot avoids it either way. | C program: loopback TCP pair; register the accepted socket with IN and HANGUP, once LEVEL with ONESHOT and once EDGE with PERSISTENT. Case A: peer sends 1 byte, then `shutdown(SD_SEND)`. Case B: peer sends 1 byte and FIN back to back. Case C: peer closes with SO_LINGER {1, 0} (RST). Log every mask from SocketNotificationRetrieveEvents and every `recv()` result. |
| 2 | After OP_DISABLE, is a separate DISABLE notification delivered, and with what bit? Is OP_ENABLE with SOCK_NOTIFY_REGISTER_EVENT_NONE accepted? Can a ONESHOT registration be re-enabled in the very next call? Does OP_ENABLE with the same completion key and a reduced filter overwrite the registration (as the ProcessSocketNotifications page says) or fail (as the concept page implies)? | Decides how disable_read and disable_write map, and whether disable then enable needs a wait. | C program: ENABLE, then DISABLE, then dequeue for 200 ms and print raw `dwNumberOfBytesTransferred` values; then ENABLE again and print `registrationResult`; repeat with filter NONE; repeat with a ONESHOT registration re-enabled right after its first notification; finally call OP_ENABLE again with the same key and only IN, and record `registrationResult` and the masks that follow. |
| 3 | Can a socket registered with ProcessSocketNotifications also carry overlapped I/O (TransmitFile, WSASend, AcceptEx) completing to the same IOCP? To a different IOCP? | Decides whether TransmitFile and AcceptEx can live inside the readiness engine. | C program: register the socket on port P; call `CreateIoCompletionPort(socket, P, key, 0)`; issue an overlapped TransmitFile; check that both packet kinds arrive. Repeat with a second port Q and record which call fails. |
| 4 | Does ProcessSocketNotifications accept AF_UNIX SOCK_STREAM sockets, sockets accepted with AcceptEx, and sockets from WSADuplicateSocket? | Decides the port IPC transport under the O1 engine. | C program: create each kind, register it, print `registrationResult`, then run a 1 MiB transfer and count IN and OUT notifications. |
| 5 | Can one WSAPoll call (and one select call) wait on an AF_UNIX socket and a TCP socket together? | Decides the port transport under the WSAPoll bring-up engine. | C program: build one WSAPOLLFD array with both kinds; make each readable in turn; check for WSAEINVAL and for correct revents. Repeat with select. |
| 6 | Which listener model costs least with per-engine IOCPs: one accepting engine with hand-off, AFD poll on the shared listener from every engine, or AcceptEx on one engine? | The one-IOCP-per-socket rule breaks today's shared listener. | Prototype on Windows Server 2022 with 4 and 8 router engines; run the io_uring harness scenarios (ret200_close c=16, ret200_ka_lo c=8, ret200_ka_hi c=256); report router CPU microseconds per request and connections accepted per engine. |
| 7 | How does WSAPoll behave on build 17763 (Server 2019) for a failed non-blocking connect, and does a timeout plus SO_ERROR check recover it? | Decides whether the bring-up engine is safe for proxying on Server 2019. | C program: non-blocking connect to a closed local port; WSAPoll with POLLWRNORM for 5 s; print revents on 17763 and on 20348; then apply the workaround. |
| 8 | What does each option cost per event at 1 to 10,000 idle connections? | The only way to rank O1, O2 and O5 on Windows. | C microbenchmark modelled on the JDK one: N idle connected sockets, one made ready per iteration; nanoseconds per wait-and-dispatch for WSAPoll, ProcessSocketNotifications (LEVEL with ONESHOT, re-arm batched; LEVEL with PERSISTENT) and wepoll; plus a 1,000-connection ping-pong; on Windows Server 2022 and Windows 11; count kernel transitions with ETW. |

- None of these experiments has been run; each answer above is a test design, not a result.
