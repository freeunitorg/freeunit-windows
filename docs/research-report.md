# Windows FreeUnit needs a new process layer

FreeUnit can be built and run natively on Windows, but not by wrapping its Unix calls: its process and IPC layer has to be rebuilt, while its event engine contract, HTTP core, message format and shared-memory layouts can stay. The rebuild replaces `fork()` with re-executed processes, gives the ports a transport without descriptor passing or per-message kernel credentials, and adds a new way to wake the workers that compete for one application queue. The audit estimates **10,000 to 18,500 new lines plus 4,000 to 8,000 changed lines before tests**, and calls the changed-lines figure a guess (research/portability-audit.md §8). The hypothesis "use I/O completion ports" is right about what a thread should wait on and wrong about how FreeUnit should do I/O. ProcessSocketNotifications delivers documented readiness through a completion port from build 20348, so the readiness engine can stay; overlapped completion I/O would replace the connection and port layers, and the fork's own io_uring work reached **parity at best** with that kind of change. The toolchain is settled by evidence: clang-cl in MSVC mode, because **340 of 6,116 exports of the official php8ts.lib carry `__vectorcall` names** that MinGW gcc cannot produce. Demand is real in general and unmeasured where a native build is the only answer: FreeUnit has never received a Windows request, and **85% of Windows hosts in DDEV's telemetry already run WSL2**. The recommendation is a conditional go: about ten weeks of small experiments and a demand poll, then a Tier 3 "development use" build whose first demo serves Drupal through the PHP module in a console on Windows 11 x64, with an exit rule.

Code references are written `path:line@872bf041` and resolve at `https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/<path>#L<line>`. The five research notes are in research/. The plan that turns this report into decisions, experiments and milestones is docs/plan.md. Claims marked "unverified" were not tested by anyone on Windows. ## 1. Upstream's "never will" names mechanisms that still need a redesign

### The refusal and its context

Upstream answered the only request for a native build in three short comments on one day. On 2021-11-27 Valentin Bartenev wrote in nginx/unit issue 604 (verified with the GitHub API):

> "@hifron Unit doesn't support native Windows interfaces and never will. It has architecture based on POSIX principles and highly tuned for \*nix kernels. There's just no way to run it on Windows without WSL2."

Twenty-eight minutes later he added: "Cygwin wouldn't help. It's just limited and slow emulation of POSIX, while Unit utilizes much more than that. Even Microsoft gave up trying to emulate \*nix interfaces over winapi in WSL1 and come up with full virtualisation of Linux kernel in WSL2." ([nginx/unit#604](https://github.com/nginx/unit/issues/604)). The issue was closed as "not planned" on 2022-06-19. It had **zero reactions**. In eight years of the archived tracker it is the only request for a native runtime; issue 1008 looks similar but asks for a Linux cross-build from a Windows host ([nginx/unit#1008](https://github.com/nginx/unit/issues/1008)). The repository was archived on 2025-10-08 (research/history-upstream-and-fork.md §1). FreeUnit's own tracker has no Windows request at all.

The Windows traces in the tree do not help. The `MINGW*` branch of configure sets `echo=auto/echo/echo.exe`, `CC=${CC:-cl}` and `NXT_WINDOWS=YES` (`auto/os/test:77-88@872bf041`, verified). Only `echo.c` and its Makefile are in the tree; nothing builds `echo.exe`, configure runs under `set -e`, and nothing reads `NXT_WINDOWS`. The branch is a remnant of the nginx layout from the 2017 initial commit, not a start (research/history-upstream-and-fork.md §4).

### Four claims, weighed one by one

"Never will" was a policy of a team that no longer maintains Unit. The decision now belongs to FreeUnit's maintainers. The other three claims deserve an answer on the merits.

"Architecture based on POSIX principles" is accurate, and the audit makes it concrete. **Every child is created by `fork()` and keeps its parent's memory** (`src/nxt_process.c:704@872bf041`); a worker's application configuration is a pointer into its prototype (`src/nxt_application.c:829@872bf041`, verified). **Ports are message-boundary socket pairs**: `SOCK_SEQPACKET` wherever the configure probe passes, else `SOCK_DGRAM` (`src/nxt_socketpair.c:16-20@872bf041`, verified). **Descriptors cross between processes that are not parent and child**: by the audit's count, 18 send sites in 15 message kinds pass one or two descriptors, including controller to router configuration pushes and segments between router and worker. **Privileged handlers authorise the sender by a kernel-supplied pid on every message** ([PR 91](https://github.com/freeunitorg/freeunit/pull/91); the audit counts 28 uses outside log messages in 6 files). **All workers of an application read one shared socket** (`src/nxt_unit.c:5976-5991@872bf041`, verified). **libunit's public API exposes `int` descriptors** (`src/nxt_unit.h:81-82@872bf041`, `:179-181`; verified). Windows has none of these in the same form. Its AF_UNIX supports only `SOCK_STREAM`, with no `socketpair`, no `SCM_RIGHTS` and no credentials ([AF_UNIX comes to Windows](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)). No shim can carry this design. On that point Bartenev was right.

"Highly tuned for \*nix kernels" was the strongest objection in 2021, and it has weakened most. All seven in-tree engines report readiness (`src/nxt_service.c:12-40@872bf041`, verified). Windows offered no documented, scalable readiness interface until ProcessSocketNotifications arrived with build 20348, the Windows Server 2022 build ([ProcessSocketNotifications](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-processsocketnotifications), verified). That gap is one reason nginx stopped at `select()` and `poll()`. In 2009 Igor Sysoev wrote that "IOCP requires another I/O concept" ([nginx list](https://mailman.nginx.org/pipermail/nginx/2009-May/011952.html)); in 2007 he had also said that he did not want to support the Windows code ([nginx list](https://mailman.nginx.org/pipermail/nginx/2007-August/001510.html)). Section 2 shows that FreeUnit can now keep its readiness engine.

"There's just no way to run it on Windows without WSL2" does not hold for the design space in 2026. PostgreSQL has re-executed its backends with `CreateProcess` since 8.0 in 2005 ([PostgreSQL 8.0.0](https://www.postgresql.org/docs/release/8.0.0/)). Apache httpd runs a Windows-specific process model ([httpd on Windows](https://httpd.apache.org/docs/2.4/platform/windows.html)). FrankenPHP shipped native Windows PHP embedding on 2026-03-06 (verified: release v1.12.0) ([FrankenPHP blog](https://dunglas.dev/2026/03/windows-support-for-frankenphp-its-finally-alive/)). What holds is the cost: the route is a second process layer that someone must maintain. The Cygwin remark also stands. Cygwin itself says that "occasional fork failures are inevitable" ([Cygwin highlights](https://cygwin.com/cygwin-ug-net/highlights.html)), so the plan uses no emulation layer.

### What the redesign replaces and what it keeps

The process model changes the most. Each child becomes a fresh `unitd.exe` started with a role argument, an explicit list of inherited handles (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) and a startup block in an inheritable section, the pattern PostgreSQL uses ([launch_backend.c](https://github.com/postgres/postgres/blob/REL_18_6/src/backend/postmaster/launch_backend.c#L417)). The prototype can stay as a resident spawner and supervisor. It keeps the router's requests for new workers and the per-application bookkeeping unchanged; only the START_PROCESS message that asks main for a new prototype carries names instead of descriptors (research/process-and-ipc-design.md D2 and D5). Only PHP and wasm lose something: their module setup ran once in the prototype before `fork()`, and now runs once per worker. Python, Perl and Ruby already start their runtimes after `fork()`. **The start-up time of a PHP worker on Windows is unmeasured.**

The IPC layer keeps its message header and queues but loses three properties of its socket. Message boundaries must come from framing. Identity moves from each message to each connection, so every writer needs its own connection to each port. Handles move by duplication, and only the more trusted process may duplicate, because a handle with `PROCESS_DUP_HANDLE` grants full control of its target ([Process Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights)). Shared-memory sections can travel by name inside a private namespace protected by its own access list, which needs no process handle at all.

The shared memory itself is the part that ports best. Request data uses a 32-bit offset relative to the field's own address (`src/nxt_unit_sptr.h:18-34@872bf041`, verified), queues hold indices and inline bytes, and segment messages name chunks by id. **No shared structure needs the same address in two processes.** That spares FreeUnit the fixed-address reattach problem that PostgreSQL fixed in 2009 ([commit message](https://www.postgresql.org/message-id/20090811115120.3931975331E%40cvs.postgresql.org)) and again in 2019 ([commit thread](https://www.postgrespro.com/list/thread-id/2436262)), that produced a new Windows reattach report in 2026 ([bug 19719](https://www.postgresql.org/message-id/19719-9eea21ac8841c776%40postgresql.org)), and that nginx solved only in 1.9.0 ([nginx commit 2ec8cfcd](https://github.com/nginx/nginx/commit/2ec8cfcd7d34415a99c3f3db3024ae954c00d0dd)).

The Linux isolation features have no Windows counterpart in the first version. Namespaces, rootfs, cgroups, capabilities and per-application users take about 3,900 lines of isolation and credential code, most of it Linux-only (research/portability-audit.md §1). For scale: nginx's Windows layer is about 6,200 lines (6,147 lines in 34 C files and headers at release-1.31.6, or 6,271 lines in 39 files at a later commit; the two notes counted different file sets) ([nginx src/os/win32](https://github.com/nginx/nginx/tree/release-1.31.6/src/os/win32)), and libuv's Windows layer is 27,099 lines ([libuv src/win](https://github.com/libuv/libuv/tree/954c1d1887bfdb223b2b0dc2201199f938902e68/src/win)).

## 2. An IOCP is the right wait object and the wrong I/O model

### The engine contract is readiness, and the io_uring work bounds the gain

FreeUnit's engine is a 21-operation readiness vtable (`src/nxt_event_engine.h:23-198@872bf041`). Handlers call `recv()` and `send()` themselves after the engine reports that a socket is ready. The io_uring contract written in this fork lists **12 places where the code base assumes readiness semantics**: the receive loop until EAGAIN, the port drain loops, a cheap BLOCKED state, a level-triggered listener shared by all router engines, synchronous buffer reuse, deferred close, and others ([engine-contract.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/engine-contract.md)). A full completion engine "would additionally invalidate items 1-2, 4, 6 and require replacing the conn-io and port-socket layers wholesale".

The io_uring effort measured what a completion-capable backend under this contract gains. Stage 1, a poll-mode bridge, kept throughput at parity and cost **+1.6% to +24.7% router CPU per request with oha and -0.6% to +49.5% with ab** (verified at commit 6ee2a59d). Stage 2, completion accept, ended at "**Net Stage-2 standing: parity-minus**"; the projected wins were "always in the deferred RECV tier", which did not land ([results-stage1.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage1.md), [results-stage2.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/results-stage2.md)). The same work found that teardown is the correctness core: a late completion against a reused slot needs generation-tagged keys, and a slot is not freed until it is quiesced ([design.md](https://github.com/andypost/unit/blob/6ee2a59dbdc3536609ec33e1fc32a14ed7e17f15/docs/io_uring/design.md)). These lessons transfer directly. **A Windows engine should be judged by parity with itself across engines, never by a speed-up over Linux.** Envoy, whose Windows build requests libevent's wepoll backend ([libevent_scheduler.cc](https://github.com/envoyproxy/envoy/blob/e04b7c217bc77b5a3c093276c84762f884dc183f/source/common/event/libevent_scheduler.cc#L23-L31)), reports worse tail latency on Windows than on Linux, "especially when TLS is involved" ([Envoy FAQ](https://www.envoyproxy.io/docs/envoy/v1.31.0/faq/windows/win_performance)).

### Six ways to wait, and why readiness through a completion port wins

| Option | Minimum Windows | Size against the epoll engine (1,225 lines) | Main problem |
|---|---|---|---|
| O1 ProcessSocketNotifications | build 20348 | 0.8 to 1.2 | young API, documentation gaps, one completion port per socket |
| O2 AFD poll (wepoll style) | Vista | 0.8 to 2.0 | undocumented driver interface |
| O3 zero-byte overlapped reads | Vista | 1.5 to 2.5 plus new connection I/O | no write readiness |
| O4 completion connection I/O | Vista | 2.0 to 2.5 plus connection and port rewrites | replaces the readiness contract |
| O5 WSAPoll | Vista; failed connects reported from Windows 10 2004 | 0.6 to 0.7 | O(n) per wait, sockets only |
| O6 select | any | 0.4 to 0.5 as a rewrite | 64 sockets by default, one provider per call |

Sizes are estimates from research/windows-io-model.md §4.

ProcessSocketNotifications fits the vtable almost one to one. It offers level, edge, oneshot and persistent triggers, registers and dequeues in one call, and ends a registration with a terminal REMOVE notification that makes teardown safe ([SOCK_NOTIFY_REGISTRATION](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/ns-winsock2-sock_notify_registration)). `PostQueuedCompletionStatus` becomes the cross-thread doorbell, and the wait call's millisecond timeout serves the timer tree. Its documentation has gaps: it names a DISABLE event that the 10.0.20348 header does not define, it does not say whether HANGUP fires on a graceful FIN, and its two pages disagree on re-registration (research/windows-io-model.md §2). All three are small experiments in the plan.

The precedents agree. nginx has carried an IOCP module since 2003; Maxim Dounin wrote in 2013 that "It's incomplete and doesn't work" ([nginx list](https://mailman.nginx.org/pipermail/nginx/2013-November/041262.html)), and nginx for Windows is still "considered to be a beta version" with one working worker ([nginx for Windows](https://nginx.org/en/docs/windows.html)). Microsoft's own Redis port emulated readiness on completions, needed "a virtual file descriptor mapping layer", and is archived ([microsoftarchive/redis](https://github.com/microsoftarchive/redis/blob/54e8c24657f4bab22f24356bd097706193727f4f/README.md)). The JDK, libuv's `uv_poll`, mio, libzmq and Envoy chose readiness through AFD poll; the JDK's selector cost stayed at about 1.43 microseconds from 1 to 10,000 channels, while the old `select()` selector grew to 932 microseconds ([nio-dev](https://mail.openjdk.org/pipermail/nio-dev/2021-April/008873.html)). The closest analogue is Pony. On 2026-06-29 (verified) it moved its Windows backend from completion IOCP to ProcessSocketNotifications, "the same model the Linux (epoll) and macOS/BSD (kqueue) backends already use", and dropped Windows 10 to do it ([ponyc 0.66.0 release](https://github.com/ponylang/ponyc/releases/tag/0.66.0)).

One note draws the opposite lesson. research/toolchain-packaging-demand.md §6.1 concludes from Node.js: "Design the I/O abstraction for completion ports, not readiness." That lesson is sound for a new runtime, which is what libuv was in 2011. It does not apply to a mature readiness core with 12 readiness assumptions outside its engine. Pony's 2026 move and the io_uring numbers are the stronger evidence for FreeUnit's case.

The answer to the hypothesis is therefore split. **A completion port is the right object to wait on**: the stage 2 engine waits on one per router thread, and child exits, signals and posts arrive on it as queued packets. **Overlapped completion I/O is the wrong first model**: it would invalidate the contract and, by the io_uring evidence, reach parity at best. Completion features enter only where a measurement shows a gain: `AcceptEx` on the listener's engine, `TransmitFile` on server editions, completion receive last.

### Engine stages, platform floor, listener and port transport

The I/O note's staged path is sound. Stage 1 is a WSAPoll engine cloned from the 737-line `src/nxt_poll_engine.c`, keyed by `SOCKET`. Its set lives in user space, so platform bugs cannot hide behind kernel registration bugs. Stage 2 is a ProcessSocketNotifications engine in level plus oneshot mode, which keeps `nxt_unix_conn_io` unchanged and, by inference, needs no end-of-file shim (experiment E06 tests it). FreeUnit has no retry-next-engine loop, so the engine must be probed before `create()`, as Microsoft's WIL probes the function with `GetProcAddress` ([wil/network.h](https://github.com/microsoft/wil/blob/f6f3069ab39fb19c1f89fa5f2d3aa8a1118ace43/include/wil/network.h#L557-L660)).

The platform floor follows from the engine and from AF_UNIX. **Build 20348 is the floor for testing and support**: Windows 11, Windows Server 2022 and Windows Server 2025. Third-party export dumps show no ProcessSocketNotifications on builds 17763 or 19045 ([ws2_32 export dump, build 19045](https://github.com/magnusstubman/dll-exports/blob/20be29379d87446b4b315e2cfdfb10eca05e345b/win10.19045/System32/ws2_32.dll.cpp); research/windows-io-model.md §2), and GitHub retired its Windows Server 2019 runner on 2025-06-30, so build 17763 cannot be tested in hosted CI ([GitHub changelog](https://github.blog/changelog/2025-04-15-upcoming-breaking-changes-and-releases-for-github-actions/)). Older builds can still run the WSAPoll engine. The I/O note keeps it for "every Windows version", with a connect timeout and an `SO_ERROR` check where WSAPoll does not report failed connects; the WSAPoll page reports them only "As of Windows 10 version 2004" ([WSAPoll](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsapoll), verified), which is build 19041. The real lower limit is AF_UNIX, which the port transport needs and which arrived after Insider build 17063 ([AF_UNIX comes to Windows](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)); build 17763 is the oldest serviced build that has it. So builds 17763 to 20347, Windows 10 1809 and later and Windows Server 2019, can run as best effort and untested. That reconciles the process note's 1809 target with the I/O note's 20348 floor. The range includes Windows 10 22H2 machines under extended security updates, which end on 2027-10-12 for consumers and 2028-10-10 for organisations ([consumer ESU](https://www.microsoft.com/en-us/windows/extended-security-updates), [ESU FAQ](https://learn.microsoft.com/en-us/lifecycle/faq/extended-security-updates)). Developers who cannot use WSL2 may well use such managed machines; that is an inference, not a measurement. Below build 17763 unitd refuses to start.

The listener needs a new shape in stage 2. ProcessSocketNotifications allows one completion port per socket, and today every router engine registers the same listening socket (`src/nxt_router.c:5250-5282@872bf041`, verified). Per-engine listening sockets are not an option: on Windows, after a second `SO_REUSEADDR` bind "the behavior for all sockets bound to that port is indeterminate", and Microsoft says that "All server applications must set SO_EXCLUSIVEADDRUSE" ([SO_REUSEADDR and SO_EXCLUSIVEADDRUSE](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse), verified). One completion port shared by all engines would deliver a connection's events to any thread, while FreeUnit's engines own their connections without locks. So one engine owns each listener and hands accepted sockets to the others through `nxt_event_engine_post()`, as Apache's accept thread feeds its workers ([child.c](https://github.com/apache/httpd/blob/2.4.69/server/mpm/winnt/child.c#L334-L347)). Microsoft's concept page warns against one completion port per thread because one thread can become a bottleneck. FreeUnit already pins connections to engines on Linux, so this is parity with Linux behaviour, not a new risk. Both the audit and the I/O note asked for a measurement before committing, against AFD poll on the shared listener and `AcceptEx` on one engine; the plan makes that comparison part of the gate of its milestone M7. In stage 1 the shared listener can stay as it is, because WSAPoll has no one-port rule and an accept herd costs nothing at development scale.

The port transport follows from the engine too. The process note chose message-mode named pipes and wrote its own condition for AF_UNIX stream sockets with a length prefix: "Choose it if the event-engine study (out of scope here) picks a readiness engine instead of IOCP, or if selector-style integrations must keep working" (research/process-and-ipc-design.md D3). The first half now holds. Stage 1 uses no completion port at all, and the I/O note states that WSAPoll and select "can wait only on sockets, which pushes the port transport to AF_UNIX stream sockets" (research/windows-io-model.md §4). The same note observes that in stage 2 a completion port can carry pipe completions next to socket notifications. That is true, but pipes would then need a helper thread in stage 1 and a completion path in the port layer in stage 2, the kind of layer the io_uring work deliberately kept in poll mode. The second half is weaker than it looks: libuv's `uv_poll` and asyncio's selector loop accept sockets only ([libuv poll](https://docs.libuv.org/en/v1.x/poll.html), [asyncio platforms](https://docs.python.org/3/library/asyncio-platforms.html)), but libuv does not use AF_UNIX on Windows ([libuv issue 2537](https://github.com/libuv/libuv/issues/2537)), so whether `uv_poll` accepts an AF_UNIX socket is unverified. **Ports therefore become AF_UNIX stream sockets with one connection per writer and length-prefixed frames, chosen for engine compatibility, not for speed.** No note measured pipes against AF_UNIX; the plan adds that benchmark (E24). Two facts are still open. ProcessSocketNotifications documents that "Only Microsoft Winsock provider sockets are supported" (verified), and whether that includes AF_UNIX sockets is unverified; AFD poll appears to work with them in wepoll and mio, in issues that are still open and without a merged test ([wepoll issue 3](https://github.com/piscisaureus/wepoll/issues/3), [mio issue 1609](https://github.com/tokio-rs/mio/issues/1609)). The peer-pid ioctl `SIO_AF_UNIX_GETPEERPID` exists in `afunix.h` but has no Microsoft reference page. The plan's fallbacks follow the experiments: if WSAPoll rejects AF_UNIX sockets, the stage 2 engine comes first and builds below 20348 are dropped; ports switch to named pipes only if WSAPoll, ProcessSocketNotifications and a zero-byte overlapped read all reject them; if the ioctl fails, a per-child token carries identity.

## 3. Clang-cl, configure under MSYS2 and the official PHP settle the build

### The PHP calling convention decides the compiler

The compiler question has a clear answer. The official PHP 8.5.11 thread-safe import library exports **6,116 names, of which 340 are `__vectorcall` names** such as `_emalloc@@8` ([php-8.5.11-Win32-vs17-x64.zip](https://downloads.php.net/~windows/releases/php-8.5.11-Win32-vs17-x64.zip)), and `Zend/zend_portability.h` selects `__vectorcall` only when `_MSC_VER` is defined ([zend_portability.h](https://github.com/php/php-src/blob/PHP-8.5/Zend/zend_portability.h); research/toolchain-packaging-demand.md §1.2). GCC has no vectorcall attribute ([GCC x86 attributes](https://gcc.gnu.org/onlinedocs/gcc/x86-Attributes.html)). A module built with MinGW gcc therefore references undecorated names that the import library does not export. That failing link has not been run yet; the name mismatch itself was read from the archives. FrankenPHP met the other half of the problem: its MinGW build crashed on a C runtime mismatch, and its shipped build uses Visual Studio's clang with lld-link against the official PHP ([FrankenPHP PR 2119](https://github.com/php/frankenphp/pull/2119), merged 2026-02-26 with 72 commits, verified). Clang-cl is expected to accept FreeUnit's GNU extensions, which plain `cl.exe` rejects: `nxt_inline` uses `__attribute__` unconditionally (`src/nxt_clang.h:11-12@872bf041`, verified) and the atomics exist only as GCC `__sync` builtins (`src/nxt_atomic.h:17-89@872bf041`, verified). Whether clang-cl compiles them unchanged is unverified (experiment E03 in the plan).

The build system stays single. FreeUnit's configure and auto/ scripts descend from nginx's, and nginx still builds its Windows zip from the same shell scripts under MSYS with 267 lines of MSVC-specific shell and makefiles at release-1.31.6: `auto/cc/msvc` (167), `auto/os/win32` (39) and three `makefile.msvc` files (61) ([nginx auto/cc/msvc](https://github.com/nginx/nginx/blob/release-1.31.6/auto/cc/msvc)). PostgreSQL removed its Visual Studio build in 17.0 and curl removed winbuild in 8.17.0, both after years of a Windows-only build system that Unix developers did not run ([PostgreSQL 17.0](https://www.postgresql.org/docs/release/17.0/), [curl 8.17.0](https://curl.se/ch/8.17.0.html)). FreeUnit needs things nginx's Windows build never needed: DLL modules linked against an import library of `unitd.exe`, the Rust static library name `otel.lib`, and perhaps `.exe` handling for its 50 run-probes. The last point is unverified: nginx skips its Unix probes on Windows, and experiment E02 shows whether MSYS2 finds `name.exe` when a probe tests `name`. Whether those 148 probes survive clang-cl under MSYS2 is the first experiment. Dependencies come from vcpkg; every library FreeUnit links has a port without platform restrictions ([vcpkg ports](https://github.com/microsoft/vcpkg/tree/master/ports)).

### The PHP module links the official build without the embed library

FreeUnit's PHP module implements its own SAPI. It calls `php_module_startup()` and the request functions, and never `php_embed_*` (research/toolchain-packaging-demand.md §1.2). It can therefore link the plain import library from the official development package, without `php8embed.lib` and without rebuilding PHP. The non-thread-safe build fits, because the module runs one request loop per process (`src/nxt_php_sapi.c:526-544@872bf041`, verified), and php.net reserves thread-safe builds for PHP "loaded as a web server module" ([PHP for Windows](https://www.php.net/downloads.php?os=windows)).

Three Windows behaviours need code or documentation. The module opens scripts with `fopen(filename, "re")` (`src/nxt_php_sapi.c:1290@872bf041`, verified). The UCRT mode parser rejects the "e" modifier, as read from the UCRT source ([UCRT source mirror](https://doxygen.reactos.org/de/dec/corecrt__internal__stdio_8h_source.html)); nobody has run it on Windows yet (experiment E20). The Windows build should therefore call `zend_stream_init_filename()`, which PHP 8.4 and 8.5 export ([zend_stream.h:69 at php-8.5.11](https://github.com/php/php-src/blob/php-8.5.11/Zend/zend_stream.h#L69), verified). That also stops a C runtime `FILE *` from crossing into `php8.dll`. **PHP's `max_execution_time` counts wall-clock time on Windows and on Apple Silicon macOS, and CPU time on Linux**: php-src arms `CreateTimerQueueTimer` on Windows, `setitimer(ITIMER_REAL)` on Apple Silicon macOS and `setitimer(ITIMER_PROF)` elsewhere ([zend_execute_API.c:1579](https://github.com/php/php-src/blob/php-8.5.11/Zend/zend_execute_API.c#L1579), [:1618](https://github.com/php/php-src/blob/php-8.5.11/Zend/zend_execute_API.c#L1618), [:1622](https://github.com/php/php-src/blob/php-8.5.11/Zend/zend_execute_API.c#L1622) at php-8.5.11, verified). A Drupal batch that waits on I/O therefore hits its limit sooner on Windows than on Linux. And opcache on Windows maps its shared memory at a fixed base and keys its mapping by user, SAPI name and an optional `opcache.cache_id` ([opcache configuration](https://www.php.net/manual/en/opcache.configuration.php)); it reattaches only when `execute_ex` sits at the creator's address and the base range is free ([shared_alloc_win32.c](https://github.com/php/php-src/blob/php-8.5.11/ext/opcache/shared_alloc_win32.c#L117)). A resident prototype keeps `php8.dll` loaded at one base. Without a per-application `cache_id`, all PHP applications of one FreeUnit instance would share one opcache, unlike Unix, where each prototype creates its own; this reading of the documentation is an inference to test.

The other runtimes sort into three groups. Python WSGI, Java and the wasm C API module fit the same MSVC-ABI toolchain; wasmtime's `x86_64-pc-windows-msvc` target is Tier 1 ([wasmtime tiers](https://docs.wasmtime.dev/stability-tiers.html)). Ruby and Perl ship as MinGW UCRT builds and would need a second toolchain. Node.js, Python ASGI and Go put FreeUnit's port descriptors into their own event loops, which on Windows accept sockets only or need a helper thread (research/portability-audit.md §4). njs has no Windows support ([nginx/njs#629](https://github.com/nginx/njs/issues/629)). The first target is PHP alone.

### Tests, CI and packaging need small, known work

The pytest suite fails on Windows before its first test. `test/conftest.py` imports `fcntl` at line 2 and `test/unit/http.py:64` looks up `socket.AF_UNIX` on every request (both verified at 872bf041). CPython 3.13 and 3.14 have no `socket.AF_UNIX` on Windows; the pull request that adds it has been open since 2025-08-05 ([cpython PR 137420](https://github.com/python/cpython/pull/137420), verified open). The harness therefore drives unitd over a loopback TCP control socket, kills process trees through a job object, scans processes with psutil and stops unitd through a control command instead of `SIGQUIT`. By the audit's regex, **68 of 110 test files match no Unix-only pattern**; the regex over-counts the Unix side and every file depends on `conftest.py`, so the portable set is uncertain in both directions. The C test table forks in `nxt_test_in_child()` and needs a `CreateProcess` re-run of the test binary instead.

Hosted Windows runners are free for public repositories, and comparable Windows legs take 2 to 20 minutes; FrankenPHP's Windows workflow had a median of 12.2 minutes per run over 15 pull-request runs from 2026-09-19 to 2026-09-21, before it cached vcpkg packages, and 10.3 minutes over the 15 completed runs from 2026-10-03 to 2026-10-07 ([FrankenPHP Windows runs](https://github.com/php/frankenphp/actions/workflows/windows.yaml), queried on 2026-10-07; research/toolchain-packaging-demand.md §6.1 and §7.1). Packaging is a zip with a nested portable `unitd.exe`, consumed by winget and an own Scoop bucket; Scoop's main bucket asks for 500 stars and 150 forks ([Scoop criteria](https://github.com/ScoopInstaller/Scoop/wiki/Criteria-for-including-apps-in-the-main-bucket)), and FreeUnit has 57 and 8 (verified). Signing is the costly part. EV certificates no longer bypass SmartScreen ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). Artifact Signing serves only organisations in listed countries and individuals in the United States or Canada ([quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)). SignPath Foundation signs open-source builds for free under its own publisher name ([SignPath terms](https://signpath.org/terms)). **The official PHP DLLs carry no embedded Authenticode signature** (catalog signatures were not checked), and on 2026-09-28 a Laravel Herd user reported Smart App Control blocking the PHP 8.4 and 8.5 extension DLLs that Herd ships ([herd-community#1757](https://github.com/beyondcode/herd-community/issues/1757)).

## 4. Demand exists, but the developers who need a native build are uncounted

### What the numbers show and what they miss

Windows is the largest operating system among developers. In Stack Overflow's 2025 survey, 49.5% use Windows for professional work and 16.8% use WSL ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology#most-popular-technologies-op-sys)). The toolchain note tabulated the public dataset ([2025 results.csv](https://github.com/StackExchange/Survey/raw/refs/heads/main/packages/archive/2025/results.csv)) and found that **respondents who have worked with PHP use Windows at work as often as everyone else: 54.0% against 54.0%** on the same basis. The published 49.5% is lower because it also counts respondents who skipped the language question. **35.3% of those PHP respondents use Windows without WSL.** The cut was computed in research/toolchain-packaging-demand.md §5.1 and not re-run here. It does not show that those developers cannot use WSL.

For Drupal the recommended tool already covers most Windows users. drupal.org recommends DDEV ([local development guide](https://www.drupal.org/docs/official_docs/local-development-guide)), and DDEV's opt-in telemetry shows **25.2% of platform rows on Windows hosts, 85% of them inside WSL2**: 4,717 WSL2, 915 Windows, 542 WSL2-mirrored and 7 WSL2-virtioproxy rows of 24,562 on 2026-10-06. Drupal 10 and 11 are 32% of its project types ([DDEV usage statistics](https://ddev.com/usage-stats/); the page shows live data that changes daily). Telemetry counts only people who already run Docker, so developers whose machines block WSL2 or virtualization are invisible in it. Their number is the open question. Docker Desktop needs a paid seat at organisations with 250 or more employees or USD 10 million in revenue ([Docker licence](https://docs.docker.com/subscription/desktop-license/)), Docker supports virtual desktops only for Business customers with nested virtualization ([Docker VDI](https://docs.docker.com/desktop/setup/vm-vdi/)), and Intune can switch WSL off per machine ([WSL Intune settings](https://learn.microsoft.com/en-us/windows/wsl/intune)). **No survey measures how often any of this happens.** WSL2 also has a known limit for local development: Microsoft still advises keeping project files in the Linux file system for speed ([WSL file systems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)), and the one upstream code change driven by a Windows host that the history search found fixed short reads over 9P (Unit 1.32.0).

Demand for PHP without a virtual machine on Windows is large in downloads. XAMPP recorded **16.4 million Windows downloads in 2025** ([SourceForge stats](https://sourceforge.net/projects/xampp/files/stats/json?start_date=2025-01-01&end_date=2025-12-31)). Laragon's 8.x line drew 1.67 million asset downloads in the 19 months since 8.0.0 was released on 2025-03-13; commercial use has needed a licence since 7.0.6 on 2024-12-16 ([Laragon releases](https://github.com/leokhoa/laragon/releases), [Laragon pricing](https://laragon.org/pricing)). Downloads are not users, and these stacks run Apache with mod_php or php-cgi. Windows has no php-fpm, php-cgi offers a static pool of at most 64 processes, and the built-in server runs one process ([php-src cgi_main.c](https://github.com/php/php-src/blob/20f4c4d605203b95cf01e76e306c25bdff6678b2/sapi/cgi/cgi_main.c#L2092-L2210), [built-in server](https://www.php.net/manual/en/features.commandline.webserver.php)). A native FreeUnit would add a dynamic process pool, per-application processes and the configuration API. FrankenPHP already offers native Windows embedding, so FreeUnit would not be alone.

### What comparable projects experienced

| Project | Windows approach | Outcome | Lesson |
|---|---|---|---|
| nginx | Unix design on Windows; select and poll | "beta" since 2009; one working worker; IOCP never finished | A port without a scalable engine stays a development tool. |
| PostgreSQL | CreateProcess re-execution, signal emulation | Native since 8.0 (2005) after about 2.5 years of merge work; reattach fixes in 2009 and 2019; a new reattach report in 2026 | Re-execution works and brings years of follow-up Windows bugs. |
| Redis (Microsoft Open Tech) | Separate fork with completion emulation | Last release 2016; archived | A sponsor-carried port ends with the sponsor. |
| Envoy | Native port led by a Microsoft engineer | Support ended on 2023-08-31 "due to a lack of resources" | Plan the exit before the start. |
| FrankenPHP | Official MSVC PHP linked with Visual Studio clang | Shipped 2026-03-06; services, timeouts and static builds still open | The PHP toolchain path is proven. |
| lighttpd | Native build since 1.4.70 | Still "experimental" | Experimental status persists without a named owner. |

Sources are in research/toolchain-packaging-demand.md §6.1 and research/history-upstream-and-fork.md §5.

FrankenPHP's port took one pull request of +532 and -149 lines (verified). That number does not transfer: the pull request built on a community branch from 2024-12-22 and on php-src changes, FrankenPHP is a Go server with threads, and Go and Caddy already ran on Windows. Its release post also claims a "3.6x" gain over "nginx plus PHP-FPM on Windows Server 2022", but php-src builds FPM only on Unix (`sapi/fpm` has no `config.w32`), so the baseline of that claim is unclear (research/toolchain-packaging-demand.md §5.7, §6.1).

The steady cost is countable. **Windows-related items are about 3% of nginx's trac tickets (85 of 2,643) and about 2.6% of PostgreSQL's master commits in 2024 and 2025** ([nginx trac](https://trac.nginx.org/nginx/query), [PostgreSQL commit search](https://github.com/search?q=repo%3Apostgres%2Fpostgres+windows&type=commits); research/toolchain-packaging-demand.md §7.1). Two costs come on top. Upstream rated Windows-only advisories in Rust dependencies as not affecting Unit: "Also not quite so urgent as we don't run on Windows" ([nginx/unit PR 1170](https://github.com/nginx/unit/pull/1170), merged on 2024-03-11), "this is a Windows only issue and so doesn't effect [sic] Unit" ([nginx/unit PR 1184](https://github.com/nginx/unit/pull/1184)), and "we're safe since it only affects Windows" ([nginx/unit PR 1226](https://github.com/nginx/unit/pull/1226)). The maintainers still merged the fixes. A native build removes that reasoning. And the fork has one maintainer, while every precedent that lost its Windows owner lost its Windows build.

### Is the effort justified

As a production platform it is not. Only 13.15% of respondents to the Perforce 2025 survey deploy PHP on Windows at all, and 4.50% use IIS, from 561 responses ([Perforce report](https://www.zend.com/system/files/2025-06/report-zend-2025-php-landscape-report_0.pdf)). As a bounded development target it can be. The companion project freeunit4drupal (https://github.com/freeunitorg/freeunit4drupal) is the first customer: it plans a Docker-free local Drupal environment on FreeUnit, macOS and Linux first, with Windows users in WSL2 until a native build exists. A native build would let one FreeUnit configuration serve Drupal on all three desktop systems, with project files on NTFS. That justifies spending a small, gated amount to measure the unknowns. It does not justify an open-ended port.

## 5. Four disagreements between the notes, and the evidence that settles each

| Question | Positions in the notes | Settlement | Winning evidence |
|---|---|---|---|
| (a) Compiler | Audit: MinGW-w64 gcc or clang (UCRT) under MSYS2 for the core, an MSVC-ABI clang only where a runtime needs it, cl.exe impractical. Toolchain note: clang-cl in MSVC mode under the MSYS2 shell for the core and the modules. | clang-cl, MSVC ABI, `/MD`, for the core and the modules. MinGW only as an optional compile check of the core. | 340 of 6,116 php8ts.lib exports are `__vectorcall` names; `ZEND_FASTCALL` is `__vectorcall` only under `_MSC_VER`; GCC has no vectorcall attribute; FrankenPHP's MinGW build failed on a runtime mismatch. One compiler for the core and the modules keeps one toolchain per process. The audit's point that run-probes need a native build stands. |
| (b) Platform floor | Process note: Windows 10 1809 and Server 2019. I/O note: build 20348, with WSAPoll on every older version and a connect workaround. Audit: Server 2022. Toolchain note: Windows 10 API floor; test only Windows 11 and Server 2022 and 2025; Server 2019 expected to work, not tested. | Tested and supported: build 20348 or later. Best effort, untested: builds 17763 to 20347 with the WSAPoll engine. Below 17763: refuse to start. | ProcessSocketNotifications needs build 20348 (verified) and is absent from 17763 and 19045 export dumps; WSAPoll reports failed connects only from build 19041 (verified), so older builds need the connect workaround; no hosted runner exists for 17763 since 2025-06-30; AF_UNIX, which the ports need, arrived after Insider build 17063, so 17763 is the oldest serviced build with it. |
| (c) Port transport | Process note and audit: message-mode named pipes, one instance per writer. Process note: AF_UNIX stream with framing if the engine is readiness-based or selector integrations matter. I/O note: readiness engine; WSAPoll waits on sockets only; a stage 2 completion port could also carry pipe completions. | AF_UNIX stream sockets, one connection per writer, length-prefixed frames. Named pipes only if WSAPoll, ProcessSocketNotifications and zero-byte reads all reject AF_UNIX. | The first half of the process note's own condition holds: stage 1 has no completion port and waits on sockets only. Pipes would need a helper thread in stage 1 and a completion path in the port layer in stage 2. Unmeasured: pipes against AF_UNIX (E24). Open: ProcessSocketNotifications with AF_UNIX (E04) and the peer-pid ioctl (E05). |
| (d) Shared listener | Audit: one completion port drained by all router threads, or an accept thread; to be settled by a test. I/O note: one owning engine with hand-off, measured against AFD poll on the shared listener and against `AcceptEx`. | Stage 1: the shared listener unchanged under WSAPoll. Stage 2: one owning engine per listener with hand-off through `nxt_event_engine_post()` as the default, confirmed by the M7 measurement against AFD poll and `AcceptEx`. | One completion port per socket (verified); a second `SO_REUSEADDR` bind is indeterminate (verified), so per-engine listeners are out; a shared completion port would deliver a connection's events to any thread, while FreeUnit's engines own their connections without locks; Apache's accept thread is a working precedent. |

Two more corrections came out of the verification, and one mapping is this report's own. The I/O note reads the port socket as `SOCK_DGRAM` because a comment says "SOCK_SEQPACKET is disabled to test SOCK_DGRAM on all platforms"; the code below it is `#if (0 || NXT_HAVE_AF_UNIX_SOCK_SEQPACKET)`, and a passing probe defines that macro to 1 (`src/nxt_socketpair.c:15-20@872bf041`, `auto/feature` and `auto/sockets:127-142@872bf041`, verified). The audit and the process note read it correctly; the conclusion that ports need message boundaries is unchanged. The notes also count the descriptor send sites differently: the audit finds 18 send sites in 15 message kinds, and the process note groups them into 16 table rows; this report and the plan use the audit's count. The console mapping is a choice, not a finding. The process note maps Ctrl+C, Ctrl+Break and console close to a fast stop and leaves the graceful stop to a control command; the toolchain note maps both keys to a graceful stop and warns that Ctrl+Break needs a shared console. FreeUnit's Unix table sends SIGINT to the fast handler and SIGQUIT to the graceful one (`src/nxt_main_process.c:151-159@872bf041`, verified). The plan therefore maps Ctrl+C to a fast stop and, by analogy with Ctrl+\ and SIGQUIT, Ctrl+Break to a graceful one, and documents `unitd --signal quit` as the reliable graceful path.

## 6. A staged path puts Drupal on Windows 11 first

The plan in docs/plan.md has one gate before any code lands in FreeUnit. **Phase 0 runs from 2026-10-12 to a decision on 2026-12-18.** It consists of 23 experiments and readings, most of them small C programs, on hosted `windows-2022` and `windows-2025` runners and one Windows 11 virtual machine, plus a three-question demand poll that the FreeUnit maintainer runs as a GitHub Discussion, linked from Drupal and DDEV channels. The gate experiments are a minimal PHP SAPI linked against the official non-thread-safe import library with clang-cl (E01), configure under MSYS2 (E02), clang-cl on the atomics (E03), WSAPoll and ProcessSocketNotifications with AF_UNIX sockets (E04), opcache reattach with a resident prototype (E11), worker start time without `fork()` (E12) and a lost-wake-up model for the application doorbell (E15). The peer-pid ioctl (E05) picks the identity variant, and the poll (E22) carries the demand condition.

If the gate passes, eight milestones follow in the FreeUnit repository. M1 adds the clang-cl build, the platform layer and typed descriptors. M2 adds re-executed processes, the job object and supervision. M3 adds the AF_UNIX transport, per-connection identity, named sections and brokered handles. M4 adds the WSAPoll engine, the router and static files. M5 adds libunit's Windows back end and the PHP module. **The first demo, targeted for 2027-06-11, installs Drupal with SQLite through the PHP 8.5 module in a console `unitd.exe` on Windows 11 x64**, serves static files and pages with four workers that share one opcache, and stops cleanly on Ctrl+C. M6 runs alongside as test harness and CI work. M7 adds the ProcessSocketNotifications engine, and M8 publishes a Tier 3 preview zip with winget and Scoop manifests, targeted for 2027-09-24.

Tier 3 "development use" is a promise with limits. It covers static files, PHP 8.4 and 8.5 non-thread-safe x64 modules, TLS and the proxy on Windows 11 and Windows Server 2022 or later, with builds from 17763 on as untested best effort. It excludes isolation, user switching, Unix-domain listeners, daemon mode, external applications, Python ASGI and Node.js. An exit rule applies: if the Windows CI job stays red for one release cycle with no owner, the next release drops the Windows build and says so. Promotion to Tier 2 needs two named maintainers, the ProcessSocketNotifications engine as the default, the HTTP-only test subset green, signed artefacts and 12 months at Tier 3 without triggering the exit rule.

## Conclusion

The Windows question for FreeUnit is a process-model question, not an I/O question. The 2021 refusal was right about the mechanisms and is overtaken on the engine: Windows now offers documented readiness through a completion port, which removes the reason nginx stalled at `select()`. What it cannot remove is the cost of a second process layer, and that cost is paid in maintainer time. The deciding variable is therefore people, not Windows. A plan that starts with ten weeks of cheap experiments, names its stop conditions and targets a development server first fits a single-maintainer fork; a plan that promises production parity does not.

Some of the work is useful even if Windows is dropped later. Typed descriptors, a narrower transport interface below the port layer, an explicit startup block for child processes and a test that keeps shared memory free of absolute pointers all make the Unix code easier to reason about. The io_uring experience sets the expectation that matters most: the goal on Windows is a correct server at parity with itself, not a faster one.
