# Windows support in NGINX Unit and FreeUnit: discussion history, source vestiges and NGINX heritage

## 1. What did users ask and maintainers answer about Unit on Windows, in order?

### Takeaway
In the whole nginx/unit history (2017-09-06 to the archival on 2025-10-08) only two issues asked for Unit, or its build tooling, on Windows without WSL: https://github.com/nginx/unit/issues/604 (2021) and https://github.com/nginx/unit/issues/1008 (2023). Both got the same answer: Windows is not supported, use WSL2 or a container. The decisive statement is Valentin Bartenev's of 2021-11-27: "Unit doesn't support native Windows interfaces and never will." FreeUnit has no Windows request at all.

### Inferences
- Upstream never debated a Windows port on its merits. Every answer was a one-line deflection to WSL2, Docker or a dev container. The only substantive reasoning is in Valentin Bartenev's two comments on issue 604 and in Igor Sysoev's 2017 code comments.
- From 2024 the "we don't run on Windows" line was used as a security triage rule for Rust dependencies. A native port would turn every such Windows-only advisory (mio IOCP named pipes, wasmtime Windows sandbox escape) into an applicable one.
- Andrew Clayton's "wider conversation about what platforms we do actually support" never happened in the archive before the upstream was archived. FreeUnit inherits an unresolved platform policy, not a decision against Windows by its own maintainers.

### Gaps
- The dump does not record who closed issue 604 or why "not planned" was chosen. The GitHub timeline API would show the actor.
- PR review summaries are absent from the dump. A review verdict on PR 1166 that mentions Windows would be missed.
- The unit mailing list (https://mailman.nginx.org/pipermail/unit/) and the unit-docs repository are outside this archive. Section 6 covers what another researcher found there.

## 2. Which technical blockers did maintainers name, and what has changed since?

### Takeaway
Maintainers named few concrete mechanisms. Valentin Bartenev cited "POSIX principles" and tuning for Unix kernels; Igor Sysoev's 2017 code comments named the specific Windows mismatches (shared memory addresses under ASLR, fork inheritance, page-locked I/O buffers, iovec layout). Mapped to today's code, the blockers are fork(), SCM_RIGHTS over AF_UNIX socketpairs, memfd or POSIX shared memory, signals, and the Unix event engines. Windows has since gained AF_UNIX stream sockets (without SCM_RIGHTS or socketpair), WSL2 with a real Linux kernel, systemd in WSL, and ProcessSocketNotifications; it still has no fork().

### Inferences
- The maintainers' "POSIX principles" maps to at least four separate mechanisms with no direct Windows equivalent in the forms Unit uses them: fork() with inherited state, datagram or seqpacket socketpairs, SCM_RIGHTS descriptor passing, and POSIX signals. Each would need a Windows design of its own, not a shim.
- Igor Sysoev's 2017 comment shows the original author knew the precise Windows obstacle for the shared memory design (address differences under ASLR, no fork() inheritance) and chose a Unix-only implementation on purpose.
- Of the WSL-specific blockers raised in the issues (memfd_create, systemd, 9P short reads), all three are resolved: two by Microsoft (WSL2, systemd support) and one by Unit (PR 1067).

### Gaps
- No maintainer ever listed Windows blockers in detail (for example IOCP versus readiness, process creation cost, handle inheritance, the select() descriptor limit). The table maps their general statements to code; the mapping is mine.
- Whether later Windows builds lifted any AF_UNIX limit listed in Microsoft's 2017 post (SOCK_DGRAM, SCM_RIGHTS, socketpair) was not checked here.
- Whether the "different addresses in different processes" problem still matters depends on whether today's port shared memory stores absolute pointers. Not checked here.

## 3. Who wanted Windows, for what, how much support did they get, and what did they settle on?

### Takeaway
Demand was small and quiet. Two people asked for Unit without WSL; neither issue received a single reaction. About ten more people show up using Unit on WSL or Docker on a Windows host, almost all for local development. Users settled on WSL2, Docker, or nothing.

### Inferences
- The demand that did surface was mostly developers on Windows laptops who want the inner development loop to work. WSL2 and Docker already serve that group, and the three concrete WSL problems raised in the tracker (memfd_create on WSL1, no systemd in WSL2, 9P short reads) are all resolved.

## 4. Which Windows vestiges are in the tree, are they reachable, and what do they say about the original intent?

### Takeaway
The vestiges are build scaffolding and comments, all written by Igor Sysoev in the 2017-01-17 "Initial version." commit. No C file ever had a Windows code path: there is no NXT_WIN32 conditional, no IOCP engine, and the `NXT_WINDOWS` and `NXT_UNIX` symbols that configure sets are read by nothing. The MinGW branch of auto/os/test cannot complete a configure run as shipped.

### Inferences
- The vestiges follow nginx's layout (a `uname`-driven OS switch, per-compiler branches, a Unix versus Windows split implied by `NXT_UNIX` and `NXT_WINDOWS`), but only the build-system half was ever written. The comments show Igor Sysoev kept Windows in mind while designing buffers, integer types and shared memory, and that he cross-tested the MinGW shell under Wine. They do not show any working Windows build of Unit.
- Igor Sysoev's remark that the proxy code "is inherited from old internal product" suggests the initial version reused an earlier code base. That would explain Windows-aware comments in a project that never targeted Windows. This is an inference; no source in the archive names the earlier product.
- For a FreeUnit port, the vestiges are neutral. None is a usable starting point. The MinGW branch would need rewriting, and the empty `nxt_mem_map_file_ctx_t` slot is the only data-structure hook that anticipates Windows.

### Gaps
- Which MSYS2 environments report a `uname -s` that matches `MINGW*` was not verified here. nginx's auto/configure matches `MINGW32_* | MINGW64_* | MSYS_*` (section 5); whether UCRT64 and CLANG64 shells report other prefixes is unverified.

## 5. NGINX heritage: what did nginx port to Windows, what was never finished, and why?

### Takeaway
nginx did port to Windows, and the port shows both what is cheap and what never got done. The cheap part shipped in 0.7.52 (2009-04-20): a native Win32 build driven by the same shell configure scripts under MSYS, with select() and, since 1.15.9 (2019), poll() through WSAPoll(). The unfinished part is the part a production server needs: an I/O completion port engine and more than one working worker. The IOCP module has been in the tree since 2003, is compiled into every Windows build, is never the default, and "doesn't work" in Maxim Dounin's words. Igor Sysoev named the reason in 2009: IOCP needs asynchronous I/O and threads, while the nginx core is built on non-blocking readiness I/O and single-threaded workers. In 2026 nginx.org still calls nginx for Windows a "beta".

### Cited Findings
A third researcher compiled this section from nginx.org, the nginx and nginx.org git histories and the nginx mailing list. I re-fetched five of its key sources (the current windows.html text, Igor Sysoev's posts of 2007-08-19 and 2009-05-02, Maxim Dounin's post of 2011-07-19, and trac ticket 2416). All matched. Source links are pinned to the nginx tag `release-1.31.6` (2026-09-15).

#### What nginx/Windows is today
- "Version of nginx for Windows uses the native Win32 API (not the Cygwin emulation layer). Only the select() and poll() (1.15.9) connection processing methods are currently used, so high performance and scalability should not be expected. Due to this and some other known issues version of nginx for Windows is considered to be a beta version." [nginx.org](https://nginx.org/en/docs/windows.html)
- Known issues, the complete list: "Although several workers can be started, only one of them actually does any work." and "The UDP (and, inherently, QUIC) functionality is not supported." [nginx.org](https://nginx.org/en/docs/windows.html#known_issues)
- Possible future enhancements, the complete list: "Running as a service.", "Using the I/O completion ports as a connection processing method.", "Using multiple worker threads inside a single worker process." The oldest copy of the page in the site repository (2011-08-11) already listed IOCP as a future enhancement. [nginx.org](https://nginx.org/en/docs/windows.html#possible_future_enhancements); [nginx.org repository](https://github.com/nginx/nginx.org/blob/488e68cfaf9c80c1ef3ad8f217a4fea6afbca0e4/xml/en/docs/windows.xml)
- The known issues used to be longer. "A worker can handle no more than 1024 simultaneous connections." was removed on 2019-02-28 with "Added the 'poll' method for Windows." The shared memory clause ("do not work on Windows Vista and later versions due to address space layout randomization") was removed on 2016-12-26. [nginx.org commit e4f29d27](https://github.com/nginx/nginx.org/commit/e4f29d27e6e009556c678d10fc34b9f6979fe8af); [nginx.org commit 57f82689](https://github.com/nginx/nginx.org/commit/57f826895dc71ff3802ae5993aeb69d45a71c3fa)
- The official zips still contain a 32-bit x86 binary: `nginx.exe` in 1.31.6 is "PE32 executable for MS Windows 6.00 (console), Intel i386", and in 0.7.52 it was "PE32 executable for MS Windows 4.00 (console), Intel i386" (read with `file`). [nginx-1.31.6.zip](https://nginx.org/download/nginx-1.31.6.zip); [nginx-0.7.52.zip](https://nginx.org/download/nginx-0.7.52.zip)
- The control API added in 1.31.5 (02 Sep 2026) is refused on Windows at configure time: "--with-control-api is not supported on Windows". [auto/modules:59-68](https://github.com/nginx/nginx/blob/release-1.31.6/auto/modules#L59-L68)

#### What was never finished, and why
- Igor Sysoev, 2007-08-19: "The native Win32 code uses select() and I/O completion port. However, this Win32-related code is not production ready and is not included in tarball. Currently I have no plan to significantly improve Win32 code because I do not think it will be faster or handy than existent Win32 solutions (IIS, etc) and because I do not want to support this code in situation when much of users have very low qualification." [nginx list](https://mailman.nginx.org/pipermail/nginx/2007-August/001510.html)
- Igor Sysoev, 2009-04-20, on 0.7.52: "No, currently it uses select(), therefore it would be slow and noscaleable. 'We call it BETA as it's better than nothing'. The next step will be IOCP with single thread, then with several threads: currently nginx is designed as single thread application, so it's required to set mutexes and locks in various places." [nginx list](https://mailman.nginx.org/pipermail/nginx/2009-April/011524.html)
- Igor Sysoev, 2009-05-02: "IOCP requires another I/O concept: it's requires asynchronous I/O while select/kqueue/epoll/etc. require non-blocking I/O. However, nginx was being developped with asynchronous I/O in mind, therefore I will add single-thread IOCP soon. It should be more scaleble than select() even with single thread. The second step, multithreaded IOCP, is more complex since nginx workers are single thread applications, and the step requires introdution various locks and mutexes." [nginx list](https://mailman.nginx.org/pipermail/nginx/2009-May/011952.html)
- Igor Sysoev, 2009-05-06: "The multi-threads version will take several months." [nginx list](https://mailman.nginx.org/pipermail/nginx/2009-May/012053.html)
- Maxim Dounin, 2011-07-19: "IOCP event module isn't complete and doesn't work. Don't try to use it." 2011-12-09: "The worker_processes under windows must be set to 1 or you must switch off accept_mutex. In either case only one worker will actually do any work." 2013-11-28: "It's incomplete and doesn't work." [nginx list 2011-07](https://mailman.nginx.org/pipermail/nginx/2011-July/028055.html); [nginx list 2011-12](https://mailman.nginx.org/pipermail/nginx/2011-December/030863.html); [nginx list 2013-11](https://mailman.nginx.org/pipermail/nginx/2013-November/041262.html)
- Maxim Dounin, 2015-04-21: "But in general it's better idea to switch to UNIX if you are going to use nginx in production." 2017-04-12, on the 1024 limit: select() "implies fixed-size bitmasks", and "1024 is the value nginx uses for official binaries to balance between maximum number of connections and unneeded overhead implied by large bitmasks." 2020-03-27: "Note though that this isn't the only limitation of nginx when running on Windows, and it's generally a bad idea to use it for production." [nginx list 2015-04](https://mailman.nginx.org/pipermail/nginx/2015-April/047291.html); [nginx list 2017-04](https://mailman.nginx.org/pipermail/nginx/2017-April/053487.html); [nginx list 2020-03](https://mailman.nginx.org/pipermail/nginx/2020-March/059217.html)
- Ruslan Ermilov, 2018-03-07: "nginx for Windows only uses one worker process, and inside it only one worker thread is created." [nginx list](https://mailman.nginx.org/pipermail/nginx/2018-March/055793.html)

#### freenginx
- freenginx keeps the same "beta" page, the same one-worker issue and the same IOCP future enhancement. Its 1.31.4 zip contains a "PE32 executable for MS Windows 5.01 (console), Intel i386". Its only Windows CHANGES entry since the fork is 1.27.3 (13 Aug 2024): "Feature: improvements in building on Windows." [freenginx.org](https://freenginx.org/en/docs/windows.html); [freenginx CHANGES](https://freenginx.org/en/CHANGES)

### Inferences
- nginx shows the shape of a cheap Windows port of an nginx-style core: keep the shell configure scripts under MSYS, add one OS file and one file per compiler, add Windows select and poll modules, and use CreateProcess instead of fork. That port reached "beta" and stayed there for 17 years.
- The unfinished part is the scalable part. Igor Sysoev named the cause: IOCP completes I/O asynchronously and wants several threads, while every other nginx event method reports readiness to single-threaded workers. Unit's engines are readiness-based too (section 6), so the same gap applies, although Unit's router already runs several worker threads.
- Unit's vestiges repeat nginx practices. Unit's comment about running the MinGW shell under Wine matches nginx's crossbuild "using Wine, mostly for compile-testing". Unit's 2017 comment that Windows ASLR breaks shared memory addresses matches nginx's pre-2016 known issue. The fixed-address remapping that nginx shipped in 1.9.0 (2015) was not adopted in Unit; Igor Sysoev kept the shared memory code Unix-only.
- nginx needed an index array for WSAPoll because Windows sockets "are not guaranteed to be small integers". Any descriptor-indexed table in Unit's select or poll engines would meet the same problem.

### Gaps
- No nginx developer explained the root cause of the one-worker limit in detail; the accept-mutex comment is the closest evidence.
- The nginx-devel archive was not searched separately, and on trac only ticket 2416 was read.
- Whether `use iocp;` still starts at `release-1.31.6` was not tested.

## 6. NGINX heritage: what did Unit's authors say publicly about design and portability?

### Takeaway
Igor Sysoev described Unit as separate, privilege-isolated processes joined by Unix socket pairs and shared memory, with epoll or kqueue in the router. No source found has him or any later maintainer speaking about Windows or portability as a goal. Maintainers discussed portability only in Unix terms: configure probes, a buildbot matrix, POSIX.1-2001 as a floor, and Solaris dropped from testing in 2020. The documented platform list was always Unix-only, and the docs mention Windows exactly once, to recommend WSL2.

### Cited Findings
Most findings in this section come from a second researcher who read the full unit mailing list archive, the unit-docs git history and Wayback snapshots. I re-fetched four of its key quotes (the keynote's process, IPC and epoll sentences; Sysoev's port definition; Bartenev's Solaris remark; the WSL2 sentence) and checked the 0.1 README, the 1.35.0 tag date and Bartenev's last commit in a full clone. All matched.

#### Igor Sysoev on the architecture
- The nginx.conf 2017 keynote, published as "Introducing NGINX Unit" by Igor Sysoev and Nick Shadrin on 2017-09-22: "all the parts are separate processes in one system. The processes are isolated for security reasons; only the main process runs as root." [NGINX blog](https://blog.nginx.org/blog/introducing-nginx-unit)
- Same keynote: "Each worker thread polls `epoll` or `kqueue` and can asynchronously work with thousands of simultaneous connections." [NGINX blog](https://blog.nginx.org/blog/introducing-nginx-unit)
- Same keynote: "So the main process forks a new process, dynamically loads the required application module in the new process, sets the appropriate credentials, and then runs the application code itself in the new process." [NGINX blog](https://blog.nginx.org/blog/introducing-nginx-unit)
- Same keynote: "The router and application processes communicate via Unix socket pairs and several shared memory segments. The socket pair and shared memory segments are private for each application process, so if an application process exits abnormally, the router process will handle this failure gracefully, and no other processes and connections will be affected." [NGINX blog](https://blog.nginx.org/blog/introducing-nginx-unit)
- Same keynote: "The key feature of Unit is dynamic configuration." The keynote page does not mention Windows, POSIX or portability. [NGINX blog](https://blog.nginx.org/blog/introducing-nginx-unit)
- Unit mailing list, 2017-09-11, subject "what "nxt_port_s" means": "The port is abstraction over Unix domain socket pair used for communication between unit processes." [unit list](https://mailman.nginx.org/pipermail/unit/2017-September/000001.html)
- GitHub, 2017-10-02: "Ports are similar to Mach ports." 2017-11-17: "The proxy code is inherited from old internal product and it is non functional at the moment." [Issue 54](https://github.com/nginx/unit/issues/54); [issue 62](https://github.com/nginx/unit/issues/62)
- Unit mailing list, 2020-12-08, to a SmartOS user choosing an event engine, Sysoev asked for the configure probe output: "checking for Linux epoll", "checking for kqueue", "checking for kqueue EVFILT_USER", "checking for Solaris event port", "checking for /dev/poll", "checking for AIX pollset". [unit list](https://mailman.nginx.org/pipermail/unit/2020-December/000231.html)
- Sysoev posted seven messages to the unit list from 2017-09-11 to 2020-12-08. None mentions Windows or portability as a goal. His last nginx/unit commit is dated 2020-10-13. [unit list archive](https://mailman.nginx.org/pipermail/unit/); [nginx/unit commits](https://github.com/nginx/unit/commits/master)

#### Event-engine heritage
- nginx documents the same pattern: "nginx supports a variety of connection processing methods. The availability of a particular method depends on the platform used. On platforms that support several methods nginx will normally select the most efficient method automatically." [nginx.org events](https://nginx.org/en/docs/events.html)
- The nginx.org front page lists among server features: "Support for kqueue (FreeBSD 4.1+), epoll (Linux 2.6+), /dev/poll (Solaris 7 11/99+), event ports (Solaris 10), select, and poll;". [nginx.org](https://nginx.org/en/)

### Inferences
- Every mechanism Sysoev named (fork, per-process credentials, a root main process, Unix socket pairs, shared memory segments, epoll or kqueue) is a Unix facility. He presented them as choices for isolation and live reconfiguration, not for portability. The stated goals a Windows port would have to keep are privilege separation, per-application crash isolation and reconfiguration without reload.
- All existing engines are readiness-based (select, poll and the Unix notification APIs). Windows I/O completion ports report completions, not readiness. A Windows engine would be the first of a different kind, unless it uses a readiness layer such as ProcessSocketNotifications (section 2).
- The Solaris precedent shows that upstream paid to test a little-used Unix platform and then stopped. A Windows port would carry a larger version of that cost, and FreeUnit would need a Windows CI runner it does not have today.
- No upstream author is left to object to, or to review, a Windows port. The decision belongs to the FreeUnit maintainers.

### Gaps
- No statement by Igor Sysoev, in English or Russian, was found on Windows, on POSIX, or on why nginx and Unit support many event engines. Pre-2017 Russian sources and the nginx.conf 2018 keynote video (no transcript) were not examined.
- Talks and podcasts by later maintainers were not searched.

## 7. Open questions for the feasibility plan

### Takeaway
The history settles what upstream thought, not what is possible in 2026. The open questions are about scope (a native unitd, a cross-build kit, or WSL2 and containers as the supported answer), about Windows designs for fork, socketpairs with SCM_RIGHTS, shared memory and signals, about the event-engine model, and about who pays for Windows CI and Windows-only security triage.

### Cited Findings
- Upstream's single production-shaped request (issue 1008) was a Linux cross-build from a Windows host, not a Windows runtime. [Issue 1008](https://github.com/nginx/unit/issues/1008)
- Microsoft recommends "the WSL container API to build production apps that use Linux runtimnes [sic]" and says WSL "has been designed and built to use with inner loop development workflows". [Microsoft Learn WSL FAQ](https://learn.microsoft.com/en-us/windows/wsl/faq)
- Windows AF_UNIX, as announced, lacks SOCK_DGRAM and SOCK_SEQPACKET, SCM_RIGHTS and socketpair. [Microsoft devblog](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)
- ProcessSocketNotifications needs Windows 10 Build 20348 or later. [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-processsocketnotifications)
- Unit always compiles its poll and select engines as fallbacks. [src/nxt_service.c:39-40](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_service.c#L39-L40)
- Upstream dropped Solaris from testing builds "due to constantly increasing burden of maintaining its support". [unit list](https://mailman.nginx.org/pipermail/unit/2020-December/000238.html)
- Upstream treated Windows-only dependency advisories as not applicable because "we don't run on Windows". [PR 1170](https://github.com/nginx/unit/pull/1170); [PR 1226](https://github.com/nginx/unit/pull/1226)
- Even on macOS the fork-without-exec model hit Objective-C runtime fork-safety aborts in 2023. [Issue 970](https://github.com/nginx/unit/issues/970)
- Isolation features rely on Linux namespaces (`CLONE_NEW*` in src/nxt_clone.h and src/nxt_clone.c). Upstream never discussed a Windows equivalent. [src/nxt_clone.h](https://github.com/freeunitorg/freeunit/blob/872bf04170756e919211799ec5574000d628d521/src/nxt_clone.h)

### Inferences
- A cross-build kit for Go (and possibly other cgo or native-extension builds) would answer the only concrete production request at a fraction of the cost of a port.
- If a native port goes ahead, the vestiges give no head start. Removing them first (as Alejandro Colomar proposed in 2024) would make the starting point honest.

### Gaps
Open questions for the feasibility plan:
1. Scope. Should FreeUnit target a native unitd, a Windows-hosted cross-build kit for Linux deployments, or document WSL2 and containers as the supported path?
2. Process model. What replaces fork() for the controller, router and application prototypes: CreateProcess with re-execution and serialized state, or a different process model? Where does Unit already exec instead of fork-without-exec (external apps were not affected in issue 970)?
3. IPC. What replaces datagram or seqpacket socketpairs and SCM_RIGHTS: Windows AF_UNIX stream sockets with DuplicateHandle, named pipes, or something else? Have later Windows builds lifted any limit in Microsoft's 2017 AF_UNIX list?
4. Shared memory. Does today's port shared memory need the same address in every process (Igor Sysoev's 2017 ASLR concern), or does it use offsets?
5. Event engine. A completion-based IOCP engine, a readiness layer through ProcessSocketNotifications (Build 20348 or later), or the existing select or poll engines (with Winsock's FD_SETSIZE and WSAPoll behaviour)? Section 5 records what nginx chose.
6. Signals and process control. What replaces SIGCHLD, SIGHUP, SIGQUIT and SIGUSR1 handling in the main process?
7. Isolation and credentials. Is there any Windows story for setuid-style credentials, namespaces, cgroups and rootfs (job objects, AppContainer), or are these features simply absent on Windows?
8. Language modules. Which runtimes embed cleanly on Windows (PHP embed SAPI, Python, Ruby, Perl, Java, Node.js, Wasm), and what does each module assume about fork and POSIX?
9. Cost. Who owns a Windows CI runner and Windows-only security triage, given the Solaris precedent?
10. Vestiges. Remove the MinGW branch, `NXT_WINDOWS`, `NXT_UNIX` and the empty `nxt_mem_map_file_ctx_t` slot now, or keep them as markers?
11. History. Who closed issue 604 as "not planned", and was there any internal NGINX discussion of Windows that never reached GitHub or the mailing list?
